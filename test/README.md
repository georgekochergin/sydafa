# Тестирование сервиса sydafa

В данном каталоге собраны модульные (unit) и сквозные (e2e) тесты, покрывающие весь функционал сервиса `sydafa`: оркестрацию инстансов СУБД, управление схемами данных, генерацию синтетических строк и проверку краевых случаев.

---

## 1. Запуск тестов

Тестирование управляется единым bash-скриптом `./test/test.sh`:

```bash
# 1. Полный цикл (рекомендуется): сборка образа, unit-тесты + сквозной e2e для всех СУБД
./test/test.sh

# 2. Только быстрые unit-тесты (запускаются внутри контейнера при сборке)
./test/test.sh --unit

# 3. Только сквозной e2e для всех баз (MSSQL и Oracle)
./test/test.sh --e2e

# 4. Сквозной e2e только для конкретной СУБД
./test/test.sh --source mssql
./test/test.sh --source oracle
```

Критерий успешности: **`100% PASS`**, итоговый код возврата (exit-code) **`0`**.

---

## 2. Структура тестов

### 2.1. Модульные тесты (Unit Tests)
Запускаются изолированно при сборке образа (`python -m unittest discover -s test`):

- **`test_api.py`** — проверка эндпоинтов FastAPI через `TestClient`:
  - `GET /health` в неинициализированном (503) и готовом (200) состоянии;
  - `GET /sources/{source}` — Safe GET без вызова `_wake`;
  - `POST /sources/{source}/activate` — корректность возврата `connection` без `parameters`, формат `activated_until` (ISO 8601 UTC);
  - Логика TTL: запрос `ttl_minutes=45` плавно ограничивается `30` минутами (cap до `MAX_TTL_MINUTES`), запрос `<= 0` сбрасывается на дефолт `15`;
  - Оркестрация: динамическое создание `POST /sources` и удаление `DELETE /sources/{source}`.
- **`test_init_apply.py`** — проверка применения манифеста `init.json`, фиксации состояния в `/state/init_state.json` и логики Self-Healing (удаление осиротевших контейнеров и томов при пустом `/state`).
- **`test_secrets.py`** — генерация и сохранение надежных случайных паролей DBA в `/state/secrets.json`.
- **`test_container_names.py`** — валидация стандартизированных сетевых имен контейнеров и томов (с префиксами и без).
- **`test_schema_engine.py`** и **`test_evolve_models.py`** — валидация DDL-компилятора общего RDBMS-слоя (`app/backends/rdbms/ddl.py`), парсинг моделей DDL/DML и ограничений целостности.
- **`test_exec_engine.py`** — построение диалектного SQL мутаций (общие + vendor-модули `backends/rdbms/{mutations,mssql/oracle/mutations}`) и валидация предикатов.
- **`test_ddl_characterization.py`** — characterization SQL диалектов MSSQL/Oracle (типы, квотирование, констрейнты) — спецификация переноса без изменения вывода.
- **`test_behavior_freeze.py`** — инвентарь сохраняемого поведения: тексты ошибок FK/cascade (HTTP 409), fallback-и, резервирование batch_id, wire-ответ SourceInfo.
- **`test_registry.py`** — реестр движков: соответствие enum моделей, отказ неизвестного типа, границы импортов backend-слоя.
- **`test_fake_backend.py`** — доказательство расширяемости: fake RDBMS-движок проходит schema+DML через общий execution без правок общих алгоритмов; не-RDBMS семейство отклоняется до подключения.
- **`test_architecture_guards.py`** — запрет вендорных ветвлений в общих модулях, Docker/драйверы вне своего слоя, Airflow без внутренних импортов.

### 2.2. Сквозные тесты (End-to-End E2E)

Сквозной e2e-сценарий реализован в `test/test_e2e_source.py` и запускается скриптом `./test/test.sh`.

#### Модель 100% изоляции и чистой остановки
- **Уникальный ID запуска (`TEST_ID=$$`)**: каждый прогон тестов изолирован по PID процесса;
- **Динамический свободный порт (`TEST_PORT`)**: скрипт автоматически находит свободный TCP-порт на хосте (`python3 -c "import socket; ..."`), что предотвращает коллизии с портом 8000, портом 8090 живого стенда и позволяет запускать параллельные тесты;
- **Изолированная Docker-сеть**: `sydafa-test-net-${TEST_ID}`;
- **Изолированный том состояния**: `sydafa-test-state-${TEST_ID}`;
- **Изолированный префикс СУБД**: `SRC_PREFIX="test-${TEST_ID}-"`, благодаря чему контейнеры именуются как `sydafa-test-${TEST_ID}-src-{type}-{name}`, а тома как `sydafa-test-${TEST_ID}-data-{type}-{name}`;
- **Гарантированная очистка (Bulletproof Cleanup)**:
  - Функция `cleanup()` перехватывает сигналы завершения (`trap cleanup EXIT INT TERM`);
  - Все контейнеры СУБД и тома удаляются динамически по фильтру префикса `^${SRC_PREFIX}`;
  - Тестовый API-контейнер `sydafa-test-${TEST_ID}`, том состояния и сеть удаляются без остатка.

Тест разворачивает чистый контейнер `sydafa` с тестовым манифестом `init.json` и проверяет реальное взаимодействие с реальными СУБД (MSSQL и Oracle):

1. **Readiness & Healthcheck**:
   - Опрос `GET /health` до появления готовности сервиса (`status: ok`) и регистрации источника в реестре.
2. **Интроспекция источника (Safe GET)**:
   - Проверка метода `GET /sources/{source}`: отдается имя рабочей базы (`sydafa`), имя читателя (`sydafa`) и плоский список таблиц. Запрос выполняется мгновенно и не будит спящий контейнер.
3. **Жизненный цикл (POST /activate)**:
   - Отправка `POST /sources/{source}/activate?ttl_minutes=45`;
   - Проверка капинга: значение `ttl_minutes` ограничено `30` минутами;
   - Проверка формата таймзоны: метка `activated_until` строго в стандарте ISO 8601 UTC (оканчивается на `Z`);
   - Проверка объекта `connection`: строка `jdbc_url` присутствует, а избыточный блок `parameters` отсутствует.
4. **DDL: Создание структуры данных**:
   - Вызов единого транзакционного метода `POST /sources/{source}/migrate`:
     - Создание схемы `e2e_demo`;
     - Создание родительской таблицы `categories` с PK `cat_id`;
     - Создание дочерней таблицы `items` с PK `item_id` и Foreign Key на `categories(cat_id)`.
5. **DML: Наполнение данными (`append`)**:
   - Вставка 3 записей в `categories` и 5 записей в `items` с автоматической поддержкой ссылочной целостности (FK-aware).
6. **DML: Параметризованный Update**:
   - Обновление строки по предикату `[{"column": "cat_id", "operator": "=", "value": 1}]`.
7. **DML: Параметризованный Delete**:
   - Удаление записи из дочерней таблицы `items` по предикату.
8. **Обработка краевых случаев и валидация (Corner Cases)**:
   - **Блокировка `truncate` родителя**: попытка выполнить `truncate` таблицы `categories` с `cascade: false` при наличии дочерних записей в `items` завершается ошибкой **HTTP 409 Conflict**.
   - **Несуществующая колонка в предикате**: попытка фильтрации по неизвестному полю в `update` завершается ошибкой **HTTP 422 Unprocessable Entity**.
   - **Недопустимый SQL-оператор**: попытка передать неподдерживаемый оператор (например, `ILIKE` в СУБД, где он запрещен) отклоняется с кодом **HTTP 422**.
9. **Комплексная эволюция схемы (DDL Evolution)**:
   - Выполнение в одном батче добавления колонки (`add_column: rating`) и последующего ее переименования (`rename_column: rating -> score`).
10. **Транзакционный откат All-or-Nothing Rollback**:
    - Отправка составного батча: первая операция корректна (`add_column: temp_probe`), вторая заведомо ошибочна (недопустимое имя колонки с пробелами `invalid name with spaces`).
    - Сервер отклоняет запрос с ошибкой **HTTP 422**.
    - Проверка через `GET /sources/{source}/schema`: колонка `temp_probe` **отсутствует** в схеме (транзакция СУБД полностью откатилась), а ранее созданная колонка `score` сохранена.
11. **Каскадная очистка (`truncate` с `cascade: true`)**:
    - Успешная каскадная очистка родительской и дочерней таблиц (**HTTP 200**).
