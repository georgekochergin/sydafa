# sydafa: создание и оформление Pull Request (gh)

Скилл для создания Pull Request через CLI-утилиту `gh` и обязательного детального
оформления его описания. Единая точка правды по git-workflow — [AGENTS.md](../../../AGENTS.md)
(раздел «Контроль веток и Pull Request (Git Workflow)»); этот скилл добавляет к нему
процедуру работы с `gh` и требования к описанию.

## Ключевые правила (из AGENTS.md, действуют всегда)

- Изменения оформляются в ветке с префиксом — именем пользователя аутентифицированного аккаунта `gh`: `<username>/<name>` (например, `georgekochergin/feature-name`); коммитить напрямую в `main` запрещено. Имя пользователя определяется на шаге проверки `gh auth status` (см. ниже).
- **Мерж запрещён**: никогда не выполняй `gh pr merge`, `git merge` в `main`, `git push` в `main` и мерж через GitHub API. Мерж осуществляет строго пользователь.
- **Один PR на задачу/диалог** без явного разрешения пользователя: доработки по замечаниям добавляй коммитами в ту же ветку и обновляй тот же PR, а не открывай новый.

## Порядок создания PR

### 1. Проверь аутентификацию `gh` (обязательно, до любых команд `gh`)

```bash
gh auth status
```

Успех — в выводе есть `✓ Logged in to github.com account <username>` для хоста `github.com`
(команда возвращает ненулевой код, если аутентификации нет). **Сразу зафиксируй
`<username>` — это префикс ветки задачи**; для машинночитаемого получения логина
используй `gh api user --jq .login`. Если вывод сообщает об отсутствии логина на
`github.com` — не запускай команды `gh` (они упадут с 401), а действуй по разделу
«Нет аутентификации» ниже и передай инициативу пользователю.

### 2. Нет аутентификации — порекомендуй пользователю

`gh auth login` — интерактивная команда с подтверждением в браузере, выполняет её
строго пользователь; агенту запускать её за пользователя не нужно.

Рекомендуй выполнить по шагам:

```bash
# основной шаг: вход на github.com по HTTPS с авторизацией через браузер (-w)
gh auth login -h github.com -p https -w
```

Дополнительные шаги, если требуются:

```bash
# gh не установлен (macOS): сначала установить
brew install gh

# после входа: настроить git credential helper, чтобы git push/pull по HTTPS
# не просил учётные данные отдельно от gh
gh auth setup-git

# финальная проверка перед повторной попыткой
gh auth status
```

Если пользователь работает по SSH-remotes, для `gh auth login` можно использовать
`-p ssh` вместо `-p https`, но каноническая рекомендация для этого репозитория — HTTPS.

### 3. Подготовь ветку и изменения

1. Убедись, что работа ведётся в ветке `<username>/<name>` (префикс — логин из шага 1), созданной от актуального `main`; если ветки ещё нет — `git checkout -b <username>/<name>`.
2. Закоммить изменения (сообщение — в стиле истории репозитория: `feat:` / `fix:` / `docs:` / `refact`, возможно со скоупом `fix(oracle):`; язык заголовков — как в истории, чаще русский).

### 4. Запушь и создай PR

```bash
git push -u origin <username>/<name>
gh pr create --title "<заголовок>" --body "<description>"
```

- Base-ветка — `main` (умолчание репозитория).
- Заголовок — краткий, отражает суть изменений; префикс типа — по характеру изменений.
- `--body` — детальное описание по обязательной структуре (следующий раздел); Markdown.
- Если часть текста описания уже готова в файле, используй `--body-file <path>`, чтобы избежать проблем с экранированием в shell.

### 5. Верни ссылку

Ссылку на созданный PR (`https://github.com/<owner>/<repo>/pull/<n>`) обязательно
включи в финальное резюме пользователю.

## Перестроение графа кодовой базы

Перестроения после каждого коммита выполняй по процедуре раздела «Граф кодовой базы (graphify)» в `AGENTS.md`: типовые правки кода — локальный `graphify update .` (без токенов), семантически значимые изменения — `extract --backend openai` с фоллбэком на локальный прогон при не настроенном `~/.config/graphify/env`.

Перед созданием PR, после последнего коммита ветки и до push, заверши работу с графом:

```sh
git add graphify-out/graph.json && git commit -m "chore: rebuild code graph"
```

- Коммит графа создаётся, только если `graphify-out/graph.json` изменён (ветки только с документацией его не трогают); остальные артефакты `graphify-out/` в коммит не попадают (белый список в `.gitignore`).
- В описании PR укажи состояние графа: перестроен локально / перестроен с LLM / семантический слой пропущен (переменные окружения не настроены). Если граф не перестраивался — тоже укажи это явно.

## Обязательное оформление description PR

Description PR обязан содержать **детальное описание изменений**. Запрещено открывать
PR с пустым, формальным («обновления», «мелкие правки») или односторочным описанием.

Структура description (по требованиям AGENTS.md):

1. **Контекст и решаемая проблема** — зачем PR, что было не так / чего не хватало.
2. **Полный скоуп изменений (Scope of Changes)** — что вошло; что сознательно не вошло, если границы неочевидны.
3. **Изменения по компонентам** — список конкретных изменений по файлам/модулям.
4. **Изменения в API / моделях / контрактах** — что поменялось в REST API, моделях, `sources.json`, DDL/DML; если ничего — явное «отсутствуют».
5. **Свидетельства тестирования** — результаты прогонов (`./test/test.sh` и его режимы), для docs-only изменений — выполненные проверки и обоснование, почему полный прогон не требовался.

Шаблон:

```markdown
## Контекст и решаемая проблема
<зачем PR, что было не так>

## Scope of Changes
<ветка/коммиты, характер изменений; что не вошло>

## Изменения по компонентам
- **`<файл/модуль>`** — <что сделано>

## Изменения в API / моделях / контрактах
<изменения или «отсутствуют»>

## Свидетельства тестирования
<прогоны и их результаты / выполненные проверки>
```

## Обновление существующего PR

Доработки по замечаниям ревью — коммитами в ту же ветку с обычным `git push`;
актуализация заголовка и описания:

```bash
gh pr edit <номер> --title "<заголовок>" --body "<description>"
```

При расширении скоупа задачи в рамках того же диалога обнови description так, чтобы
он полностью описывал все изменения в ветке, а не только последнюю доработку.

## Чек-лист перед созданием PR

- [ ] Ветка `<username>/<name>` от актуального `main` (префикс — логин аутентифицированного пользователя `gh`), прямых коммитов в `main` нет.
- [ ] `gh auth status` проверен; аутентификация на `github.com` есть.
- [ ] Все изменения задачи закоммичены в эту ветку (один PR на задачу/диалог).
- [ ] Граф кодовой базы перестроен по процедуре AGENTS.md; `graph.json` закоммичен финальным коммитом, состояние графа отражено в описании PR.
- [ ] Тесты запущены; для docs-only — проверки выполнены и описаны.
- [ ] Description детальное, по обязательной структуре из пяти разделов.
- [ ] В финальном резюме есть ссылка на PR; мерж не выполнялся.
