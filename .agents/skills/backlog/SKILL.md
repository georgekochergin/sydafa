# sydafa: ведение бэклога (backlog.md)

Скилл для работы с бэклогом проекта — файлом `docs/backlog.md`.

## Размещение и режим доступа

- Бэклог — это всегда файл `docs/backlog.md` (каталог `docs/`). Не создавай бэклог в других местах и не дублируй его.
- **Заполнять и как-либо изменять `backlog.md` можно только по явному требованию пользователя или с его разрешения.** Никогда не добавляй, не редактируй и не удаляй записи по собственной инициативе — в том числе «попутно», выполняя другую задачу и обнаружив проблему: сначала предложи внести запись в бэклог и дождись согласия.
- Чтение бэклога (показать записи, ответить «что в бэклоге», найти задачу) разрешения не требует.

## Структура файла

1. Заголовок `#` и короткая преамбула (1–2 предложения: что фиксирует документ и правило пополнения).
2. **Оглавление** — сразу после преамбулы, для навигации по бэклогу: нумерованный список ссылок на все записи (анкоры заголовков `##`), с приоритетом каждой записи рядом. Обновляй оглавление при каждом изменении набора, названий или приоритетов записей.
3. Записи — по одному блоку `## N. <Название задачи>` на задачу, с нарастающей нумерацией. По умолчанию новые записи добавляются в конец файла со следующим номером; если пользователь явно просит порядок по важности, соблюдай его. При добавлении нескольких записей по важности размещай их от наиболее важной к наименее важной, не переставляя существующие записи без запроса.
4. У каждой записи сразу после заголовка обязательны метаданные `Дата добавления: YYYY-MM-DD`. Для новой записи используй текущую дату; для существующей сохраняй исходную дату. Если дата существующей записи неизвестна, уточни её у пользователя, не выдумывай. Дата не является дополнительным подразделом: четыре обязательных подраздела сохраняются.

## Обязательная структура записи

Каждая запись состоит ровно из четырёх подразделов в указанном порядке.

### `### Контекст`
Термины и определения, выжимки из документации проекта (`README.md`, `AGENTS.md`) и ссылки на файлы кода (`app/...`). Отвечает на вопрос «что нужно знать, чтобы понять задачу». Не содержит описания самой проблемы.

### `### Проблема`
Описание проблемы, конкретный пример и кейс воспроизведения (шаги/окружение, в которых проблема проявляется).

### `### Предпочтительный путь решения`
**Ровно один** вариант решения — без перечня альтернатив и сравнительных матриц. Допустимы краткое обоснование выбора и этапы реализации. Если ранее рассматривались альтернативы, в бэклог попадает только выбранный путь; прочее отбрасывается или сжимается в одну фразу обоснования.

### `### Приоритет`
Одно из двух значений: `` `важно` `` или `` `можно отложить` ``.
Значение **всегда уточняется у пользователя** и не назначается самостоятельно. Если пользователь не назвал приоритет — задай вопрос (например, через AskUserQuestion) до сохранения записи. Если в исходном тексте задачи уже есть явная пометка (например, «задача отложена»), используй её.

## Шаблон записи

```markdown
## N. <Краткое название задачи>

Дата добавления: YYYY-MM-DD

### Контекст
<термины и определения, выжимки из документации, ссылки на код>

### Проблема
<описание>

Пример: <конкретный пример>.

Кейс воспроизведения: <шаги/окружение, в которых проблема проявляется>.

### Предпочтительный путь решения
<единственный вариант решения; при необходимости — этапы реализации>

### Приоритет
`важно` | `можно отложить`
```

## Правила редактирования

- Реструктуризация существующей записи: сохрани фактическое содержание, перераспределив его по четырём подразделам; альтернативные варианты решения отбрасывай, оставляя один предпочтительный; приоритет выясни у пользователя, если он ещё не указан.
- Удаление записи или пометка её выполненной — только по отдельному запросу пользователя.
- Язык записей — русский; проектные термины (`entity_fqn`, `ref_entity_fqn`, `sources.json`, `/state` и т.п.) — в точности как в коде и документации.
- Приоритетные записи (`важно`) размещаются в оглавлении с пометкой. По умолчанию изменение приоритета не меняет порядок записей; явное указание пользователя о сортировке имеет приоритет. При перестановке согласованно обновляй нумерацию и ссылки оглавления.

## Анкоры для оглавления

GitHub строит анкор из заголовка: нижний регистр, удаление знаков препинания (точка после номера отбрасывается), пробелы → дефисы; кириллица сохраняется.
Пример: `## 1. Apache Kafka как источник данных sydafa` → `#1-apache-kafka-как-источник-данных-sydafa`.
