## 1. Apache Kafka как источник данных sydafa

Дата добавления: 2026-10-28

### Контекст

- `sydafa` — автономная среда синтетической эмуляции хранилищ данных (DWH / Data Lake) с транзакционной эволюцией схем и связными синтетическими генераторами (см. [README.md](README.md)).
- В реальных архитектурах КХД значительная часть данных поступает не только батчами из реляционных СУБД (MSSQL, Oracle), но и непрерывными потоками событий из **Apache Kafka**: CDC-стримы изменений операционных баз, шины событий микросервисов, финансовые транзакции, IoT/clickstream.
- Текущий контракт API уже готов к стриминговым сущностям:
  - `entity_fqn`: для реляционных источников — `schema.table`, для Kafka — имя топика (`domain.topic_name`);
  - `ColumnSpec` покрывает структуру payload сообщений топика (`bigint`, `string`, `decimal`, `timestamp`, `uuid`);
  - `primary_key` в Kafka определяет Message Key (партиционирование и compaction);
  - `foreign_keys` / `ref_entity_fqn`: брокер не поддерживает реляционные констрейнты, но генератор sydafa создаёт в памяти согласованные пулы идентификаторов (события топика `demo.transactions` используют валидные `account_id` из топика `demo.accounts`);
  - `TableRuleProfile` и инварианты (например, `cumulative_balance`) генерируются построчно в памяти и ложатся на поток сообщений;
  - Safe GET (RFC 7231): чтение метаданных топиков (`GET /sources/{source}/schema`, `GET /sources/{source}/rules`) идёт из локального состояния `/state` без запуска контейнера брокера.

### Проблема

sydafa поддерживает только реляционные батч-источники: невозможно объявлять и оркестрировать топики Kafka как полноправные источники данных с синтетической генерацией событий, инвариантами связности и единым транзакционным API миграций.

Кейс воспроизведения: инженер ETL/DWH хочет протестировать загрузку в своё хранилище CDC-стрима — вставок, обновлений и удалений с `before`/`after`-состояниями строк. Сегодня для этого нужно вручную поднимать брокер, Debezium и наполнять события, без генераторов, инвариантов и оркестрации sydafa.

### Предпочтительный путь решения

Новый тип источника на связке **PostgreSQL (`wal_level=logical`) + встроенный CDC-воркер логической репликации → Redpanda**: полный цикл `append` / `update` / `delete` / `truncate` исполняется нативно в СУБД, а воркер транслирует изменения в топики в промышленном CDC-формате (`op: "c" | "u" | "d"`, `before`/`after`, метаданные `txId`, `lsn`, `ts_ms`; `delete` дополнительно отправляет tombstone `key=PK, value=null`).

Этапы реализации:

1. **Драйвер Redpanda**: контейнер `docker.redpanda.com/redpandadata/redpanda:latest` (dev-режим, минимальный RAM), управление топиками через Kafka AdminClient.
2. **PostgreSQL storage backend**: `wal_level=logical`, слот репликации `pg_create_logical_replication_slot('sydafa_cdc', 'pgoutput')`.
3. **Легковесный асинхронный streaming worker** (`asyncpg`/`psycopg2` + `confluent-kafka`/`aiokafka`): читает события WAL и отправляет их в топики Redpanda.
4. **Migration LSN Barrier**: фиксация LSN транзакции в `app/backends/rdbms/execution.py` (после рефакторинга source-адаптеров) и ожидание отправки всех событий до ответа на `POST /migrate` (компенсация асинхронности доставки).

Обоснование выбора: полное сохранение транзакционной семантики DML и реалистичный enterprise-формат CDC. Альтернативы отклонены — «чистый» брокер не даёт нативных UPDATE/DELETE (только эмуляция tombstone), гибрид двух драйверов удваивает поддержку кодовой базы.

## 2. Единый механизм очистки данных источника без удаления тома

Дата добавления: 2026-10-28

### Контекст

- Данные источника живут в named volume `{prefix}{source}-data`; состояние — в `/state` (секреты, статус, сиквенсы ключей, батчи).
- `reset_data_volume` в `app/container_manager.py` различает два случая: том подключён к sydafa под `/source-volumes/` — содержимое очищается, том сохраняется; подключения нет — том удаляется и пересоздаётся через Docker API. Та же развилка используется self-healing в `app/init_apply.py`.
- Docker API позволяет создать или удалить том, но не «стереть файлы внутри»: для очистки содержимого нужен контейнер, к которому том подключён.
- Сохраняющееся ограничение Compose (не решается этим механизмом): при добавлении источника том с точным `name` нужно вручную объявить в Compose-файле потребителя и подключить к сервису (например, для источника `crm` — `${SYDAFA_CONTAINER_PREFIX:-sydafa}-data-mssql-crm` и `sydafa_crm_data:/source-volumes/crm`, включая `test/docker-compose.override.yaml` с `!override`); применение — `docker compose up -d sydafa`, не `restart`. Полное удаление томов — только `docker compose down --remove-orphans --volumes`.

### Проблема

Единая по смыслу операция «сбросить данные источника» (`POST /sources/{source}/reinit`, self-healing) реализуется по-разному в зависимости от окружения, а при подключённом томе упирается в запрет Docker удалять подключённый том.

Кейс воспроизведения: источник `bank` использует том `sydafa-data-mssql-bank`, который в Compose-стенде подключён одновременно к MSSQL и к sydafa (`/source-volumes/bank`). После удаления контейнера MSSQL Docker запрещает удалить том — он используется контейнером sydafa, поэтому `/reinit` очищает файлы через подключённую директорию. При запуске sydafa standalone без такого подключения тот же вызов `/reinit` удаляет и пересоздаёт том. Внешнее поведение API одинаково, способ сброса — разный.

### Предпочтительный путь решения

При любом сбросе очищать **содержимое** тома через временный служебный контейнер, сам том всегда сохранять — независимо от наличия подключений:

1. Под блокировкой источника остановить и удалить его контейнер СУБД; при ошибке удаления не начинать очистку файлов работающей базы.
2. Через Docker SDK запустить временный служебный контейнер, подключив только нужный том; очистить всё содержимое, включая скрытые файлы и вложенные каталоги, не переходя по символическим ссылкам за пределы тома. Образ служебного контейнера и права доступа выбрать явно, не полагаясь на наличие shell в образах СУБД.
3. Дождаться успешного завершения и удалить служебный контейнер, в том числе при ошибке или таймауте; при неуспехе не сообщать об успешном сбросе источника.
4. Применить механизм в `/reinit` и self-healing вместо развилки «очистить подключённый том / удалить неподключённый». Удаление самих томов оставить операцией полного демонтажа: `docker compose down --remove-orphans --volumes`.

Критерии приёмки: полный e2e `/reinit` на MSSQL и Oracle в обоих окружениях (том подключён к sydafa / доступен только через Docker) — том сохраняется, содержимое сбрасывается, схема из манифеста разворачивается повторно; покрыты self-healing, скрытые файлы, вложенные каталоги, символические ссылки, ошибки/таймауты и конкурентные операции над одним источником; чужие тома и источники не затрагиваются, служебные контейнеры не остаются; Compose-контракт сохранён (без `--volumes` данные остаются, с `--volumes` — удаляются объявленные тома).

### Приоритет

`можно отложить` — задача отложена: текущую реализацию не заменять в рамках доработки Compose cleanup.

## 3. Согласованная фиксация БД и состояния /state

Дата добавления: 2026-10-29

### Контекст

Миграции исполняются в `app/backends/rdbms/execution.py` (после рефакторинга source-адаптеров; ранее — `exec_engine.py`). Структура таблиц, сиквенсы и журнал эволюции сохраняются отдельно от СУБД через `app/schema_state.py`. Исходное наблюдение: SIDE-03 в плане `sydafa-source-adapters-plan.md` от 2026-10-29 (`~/ai_plans/dlh_poc/2026-10-29/`).

### Проблема

Commit БД предшествует сохранению LiveSchema, синхронизации sequence transitions и записи evolution log. Сбой процесса или файловой системы в этом окне оставляет физическую БД и метаданные рассогласованными; общей транзакции между ними нет.

Кейс воспроизведения: внедрить отказ записи `save_live_schema()` после успешного commit, перезапустить API и сравнить физический каталог с `/sources/{source}/schema`. Это сценарий для проверки; при анализе runtime-воспроизведение не выполнялось.

### Предпочтительный путь решения

Спроектировать и внедрить протокол фиксации и восстановления с durable operation journal: определить authoritative state, фиксировать стадии операции и при рестарте выявлять и восстанавливать незавершённую публикацию метаданных. Покрыть fault injection до/после commit и каждой записи состояния. Атомарную замену одного JSON не считать общей транзакцией; уже выделенные sequence/batch значения не возвращать для повторного использования.

## 4. Честный транзакционный контракт Oracle DDL и TRUNCATE

Дата добавления: 2026-10-29

### Контекст

`app/backends/rdbms/execution.py` выполняет DDL и DML одним батчем; физическую очистку строит `dialect.clear_table()` в `app/backends/rdbms/mutations.py` (без dependents — SQL TRUNCATE). README и docstring execution engine описывают All-or-Nothing. Внутренние границы транзакций движков уже описаны `TransactionSemantics` в `app/backends/rdbms/contracts.py` (рефакторинг адаптеров); матрица гарантий в документации и физические failure-тесты остаются в этой задаче. Исходное наблюдение: SIDE-01 в плане от 2026-10-29.

### Проблема

Oracle DDL и TRUNCATE выполняют неявные commit: последующий `rollback()` не отменяет весь батч. Клиенту обещана гарантия, которую текущее исполнение не обеспечивает, а JSON LiveSchema может не отражать частично применённый DDL.

Кейс воспроизведения: в одноразовом Oracle-источнике выполнить успешную DDL, затем операцию с ошибкой на стадии исполнения, и проверить физический каталог после отказа. Вывод основан на коде и семантике Oracle; runtime-сценарий при анализе не запускался.

### Предпочтительный путь решения

Зафиксировать честную матрицу транзакционных гарантий по движкам и операциям, сохранить текущий набор операций и документировать ограничения Oracle вместо безусловного All-or-Nothing. Согласованно обновить README, AGENTS и API-скилл; добавить физические failure-тесты DML, DDL и TRUNCATE. Не объявлять компенсацию или общую атомарность реализованной наличием вызова rollback.

## 5. Сериализация изменяющих операций над источником

Дата добавления: 2026-10-29

### Контекст

`app/container_manager.py` использует lock во время `wake_up()`. В `app/main.py` выполнение миграции начинается после возврата wake. Резервирование сиквенсов изменяет cache и JSON в `app/schema_state.py`. Исходное наблюдение: SIDE-08 в плане от 2026-10-29.

### Проблема

Lifecycle lock не охватывает весь migrate-сценарий; параллельные migrate/reinit/deactivate и резервирования состояния имеют незащищённые окна. Threading lock также не обеспечивает межпроцессной синхронизации.

Кейс воспроизведения: синхронизированно запустить две миграции одного источника либо migrate одновременно с reinit/deactivate и проверить строки, LiveSchema и диапазоны ключей. Конкретная потеря данных при анализе не воспроизводилась.

### Предпочтительный путь решения

Сериализовать полный изменяющий сценарий по source в поддерживаемом однопроцессном режиме, включая миграцию, reinit, deactivate и выделение диапазонов. Разместить блокировку в orchestration, не в vendor adapter; обеспечить согласованное повторное вхождение для init/wake. Проверить конкурентные операции и независимость разных источников. Явно описать ограничение одним процессом, не заявляя multi-worker гарантий.

## 6. Изоляция очистки ресурсов e2e текущим прогоном

Дата добавления: 2026-10-29

### Контекст

`test/test.sh` создаёт уникальные TEST_ID, сеть, порт и префикс ресурсов. Скрипт также содержит предварительную зачистку `sydafa-test-*` и удаление контейнеров по общим тестовым признакам. Исходное наблюдение: SIDE-07 в плане от 2026-10-29.

### Проблема

Широкие cleanup-фильтры не ограничены текущим TEST_ID и способны удалить контейнеры другого активного тестового прогона. Уникальные сеть/порт сами по себе не обеспечивают заявленную безопасность параллельных тестов. Затрагивание живого нетестового стенда этим наблюдением не установлено.

Кейс воспроизведения: создать ресурсы двух тестовых прогонов и выполнить startup cleanup либо exit cleanup одного; проверить сохранность ресурсов второго. Разрушительная проверка на действующих контурах при анализе не выполнялась.

### Предпочтительный путь решения

Ограничить автоматический cleanup точными именами и ownership-метками текущего TEST_ID. Удаление старых ресурсов вынести в отдельную явно запускаемую процедуру с проверкой принадлежности. Добавить проверку, что cleanup одного прогона сохраняет ресурсы другого; синхронизировать документацию о тестовой изоляции.

## 7. Явный отказ при ошибке проверки инварианта

Дата добавления: 2026-10-29

### Контекст

`app/backends/rdbms/generation.py:validate_table_invariants()` проверяет cumulative_balance SQL-запросом (после рефакторинга адаптеров; ранее — `rules_state.validate_table_invariants_on_data`). Функция вызывается при проверке правил и изменяющих операций. Исходное наблюдение: SIDE-09 в плане от 2026-10-29.

### Проблема

При исключении проверочного SQL функция логирует warning и назначает `violations = []`. Невыполненная проверка трактуется как отсутствие нарушений, поэтому изменение может быть допущено без подтверждения инварианта. Наблюдение относится к этой функции, а не автоматически ко всем механизмам генерации.

Кейс воспроизведения: подменить execute проверочного запроса исключением и вызвать validator; проверить, что ошибка сейчас подавляется.

### Предпочтительный путь решения

Перевести проверку в fail-closed: при ошибке чтения возвращать явную ошибку проверки и не применять изменение, требующее подтверждения инварианта. Сохранить безопасную диагностику исходной причины; покрыть тестами validator, API и transaction path, включая rollback при неуспешной проверке.

## 8. Физическая проверка rollback в e2e

Дата добавления: 2026-10-29

### Контекст

В `test/test_e2e_source.py` раздел All-or-Nothing Rollback отправляет батч с корректной колонкой и колонкой с пробелами в имени, затем читает `/sources/{source}/schema`. Исходное наблюдение: SIDE-02 в плане от 2026-10-29.

### Проблема

Pydantic отвергает весь запрос до handler: первая SQL-операция не исполняется. Проверяется JSON-схема, а не физическая БД. Зелёный тест не доказывает откат выполненного SQL и не обнаруживает рассогласование данных и состояния.

Кейс воспроизведения: проследить вызовы execution engine для существующего failing_batch — ошибка имени возникает при разборе request, до выполнения миграции.

### Предпочтительный путь решения

## 12. Fail-open предзагрузка балансов и тихий пропуск валидации

Дата добавления: 2026-10-29

### Контекст

- `GenerationSession._preload_state()` в `app/backends/rdbms/generation.py` предзагружает накопительные балансы инварианта `cumulative_balance` SQL-запросами `SUM` по таблице; любые исключения при чтении подавляются (`except Exception: pass`).
- `validate_table_invariants()` в `app/backends/rdbms/generation.py` молча завершается успехом, если таблицы нет в live-схеме (`return` без проверки).
- Запись №7 покрывает fail-open проверочного запроса; здесь — две другие точки того же семейства. Исходное наблюдение: D-6 в `proposal-1.md` от 2026-10-29 (`~/ai_plans/dlh_poc/2026-10-29/`); рефакторинг source-адаптеров сохраняет текущее поведение (characterization-тест) и не включает исправление.

### Проблема

Сбой чтения балансов не прерывает генерацию: балансы считаются с `initial_balance`, и `append` может тихо нарушить `min_balance`; валидация таблицы, отсутствующей в live-схеме, трактуется как «нарушений нет».

Пример: `append` в таблицу с `cumulative_balance` при ошибочном чтении `SUM` начинает транзакции от нулевого остатка вместо фактического — сгенерированные списания проходят проверку инварианта, хотя реальный баланс мог уйти ниже `min_balance`.

Кейс воспроизведения: подменить исключение `execute` при предзагрузке балансов и выполнить `append`; отдельно вызвать валидацию для `entity_fqn`, отсутствующего в live-схеме. Runtime-воспроизведение при анализе не выполнялось.

### Предпочтительный путь решения

Перевести обе точки на явную семантику: ошибка чтения балансов — ошибка операции генерации (без допуска «по умолчанию»), отсутствие таблицы в live-схеме — явная ошибка валидации. Сохранить безопасную диагностику исходной причины; покрыть тестами генерацию и оба пути валидации. Ужесточение выполнять отдельным поведенческим изменением после рефакторинга адаптеров.

### Приоритет

## 13. Масштабируемый выбор FK-родителя без полной выгрузки таблицы

Дата добавления: 2026-10-29

### Контекст

- `pick_existing_pk()` в `app/backends/rdbms/data.py` выбирает родителя для FK: `SELECT <pk> FROM <parent>` без ограничений, `fetchall()` всех строк и `random.choice`.
- Вызов выполняется на каждую генерируемую строку с FK (`_resolve_fk_values` → `mint_new_row`, оба в `app/backends/rdbms/generation.py`); `AppendOp` допускает до 100 000 строк за операцию.
- Проблема производительности, не блокирующая рефакторинг source-адаптеров; исходное наблюдение — верификация кода в `proposal-1.md` от 2026-10-29.

### Проблема

Стоимость выбора одного родителя — O(|parent|), суммарно O(rows × |parent|): на больших родительских таблицах `append` деградирует на порядки.

Пример: `append` 10 000 строк в дочернюю таблицу при 100 000 строк в родителе — до 10⁹ прочитанных строк и соответствующий трафик PK по сети на один вызов.

Кейс воспроизведения: инициализировать родителя 100 000 строк, замерить время `append` 1 000 строк в дочернюю таблицу; повторить при 200 000 строк родителя — время растёт линейно от размера родителя, а не от количества строк append.

### Предпочтительный путь решения

Выбирать случайного родителя средствами СУБД (единый контракт в RDBMS-слое после рефакторинга: MSSQL — `ORDER BY NEWID()`/`TABLESAMPLE`, Oracle — `dbms_random` + `FETCH FIRST`) с сохранением семантики Strict FK Integrity: значения только из существующих строк родителя, при пустом родителе — прежний 409. Критерий приёмки — время `append` линейно по `rows` и не зависит от |parent|.
