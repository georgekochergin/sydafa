# sydafa — Инструкции проекта

## Контекст и архитектура
- Автономный сервис эмуляции СУБД, оркестрации контейнеров через Docker SDK, транзакционной эволюции схем данных (API-first) и синтетической генерации данных (FK-aware).
- Стек: Python 3.12, FastAPI, Uvicorn, Pydantic v2, pymssql, oracledb, Faker, Docker Python SDK.
- Источники поднимаются лениво (`wake_up`): не в `lifespan`. Данные — named volume `{prefix}{source}-data`; секреты — `/state/secrets.json`; статус — `/state/source_status.{source}.json`.
- Принцип Safe GET (RFC 7231): GET-эндпоинты (`/sources/{source}`, `/sources/{source}/schema`, `/sources/{source}/status`, `/health`) безопасны и читают только из тома `/state` и памяти; они не запускают контейнеры СУБД. Контейнер физически поднимается только через POST `/activate` или POST `/exec`.
- Публичный аккаунт: `sydafa` / `sydafa` (только чтение). Внутренний DBA со случайным логином и паролем в `/state/secrets.json`. `sa` DISABLE, `pdbadmin` DROP.
- Внешний host-порт публикуется через `SYDAFA_EXT_PORT_{SOURCE}` и возвращается в объекте `connection`. Объект `connection` содержит готовый `jdbc_url` (поле `parameters` удалено как избыточное). Поле `activated_until` всегда в формате ISO 8601 UTC (`Z`).
- Источники данных объявляются в `init.json` (включая пустые базы `"mssql": []`).
- `/health` = готовность API, не прогрев СУБД.

## Git
- Все новые изменения оформляются в отдельных ветках с префиксом `kodik/` (например, `kodik/feature-name`).
- Запрещено коммитить напрямую в `main`.
- Обязательно создавай Pull Request и возвращай ссылки на pull request (-ы) в финальном резюме по доработкам.

## Скилл sydafa-api
- При любых изменениях в коде, затрагивающих REST API (ручки, модели запросов, операции `op`, типы колонок, генераторы), проверяй актуальность скилла `.agents/skills/sydafa-api/SKILL.md` и обновляй его при необходимости.

## Testing
- Обязательное правило: Любой новый или измененный функционал (эндпоинты, параметры, логика генераторов, операции DDL/DML) должен сопровождаться модульными тестами (в папке `test/`) и проверяться сквозным e2e-сценарием (`./test/test.sh`). Не допускается сдача задач и мерж при непройденных проверках.
- Изоляция тестирования: e2e-тесты (`./test/test.sh`) полностью изолированы (уникальный `TEST_ID=$$`, динамический свободный порт `TEST_PORT`, сеть `sydafa-test-net-${TEST_ID}`, префикс контейнеров `sydafa-test-${TEST_ID}-`). Тесты безопасны для параллельного запуска с работающим живым стендом КХД и гарантированно удаляют 100% созданных контейнеров, сетей и томов по завершении (через `trap cleanup EXIT INT TERM`).
- Стандартный сценарий полной проверки сервиса (unit + e2e):
  `./test/test.sh`
- Запуск только сквозного e2e-тестирования СУБД (MSSQL -> затем Oracle) в Docker:
  `./test/test.sh --e2e`
- Запуск тестирования конкретного источника:
  `./test/test.sh --source mssql` или `./test/test.sh --source oracle`
- Запуск быстрых unit-тестов внутри Dockerfile при сборке:
  `./test/test.sh --unit` (или `docker build -t sydafa:latest .`)
- Критерий успешности: 100% прохождение тестов (PASS всех этапов, exit-code 0).
