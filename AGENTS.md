# sydafa — Инструкции проекта

## Контекст и архитектура
- Автономный сервис эмуляции СУБД, оркестрации контейнеров через Docker SDK, транзакционной эволюции схем данных (API-first) и синтетической генерации данных (FK-aware).
- Стек: Python 3.12, FastAPI, Uvicorn, Pydantic v2, pymssql, oracledb, Faker, Docker Python SDK.
- Источники поднимаются лениво (`wake_up`): не в `lifespan`. Данные — named volume `{prefix}{source}-data`; секреты — `/state/secrets.json`; статус — `/state/source_status.{source}.json`; сиквенсы ключей — `/state/sequences.{source}.json`; батчи — `/state/batch_sequence.{source}.json`.
- Монотонность сиквенсов (Zero Key Resurrection): генератор `sequence` и первичные ключи работают по персистентным монотонным счетчикам в `/state/sequences.{source}.json` (старт с 0, инкремент на каждый батч) без чтения таблиц БД (`SELECT MAX`). Значения сиквенсов строго возрастают и никогда не переиспользуются после `delete` или `truncate`.
- Первичные ключи (Primary Key): одиночный PK обязан содержать уникальный генератор (`sequence` или `uuid`); составной PK обязан содержать как минимум одну уникальную колонку (`sequence` или `uuid`) либо состоять из колонок `foreign_keys`.
- Внешние ключи (Strict Foreign Key Integrity): операция `append` не содержит параметра `new_key_ratio` и не выполняет неявных вставок в родительские таблицы. Значения FK берутся исключительно из существующих строк родителя. При пустом родителе операция `append` возвращает ошибку 409 Conflict.
- Принцип Safe GET (RFC 7231): GET-эндпоинты (`/sources/{source}`, `/sources/{source}/schema`, `/sources/{source}/status`, `/sources/{source}/rules`, `/health`) безопасны и читают только из тома `/state` и памяти; они не запускают контейнеры СУБД. Контейнер физически поднимается только через POST `/activate` или POST `/migrate`.
- Публичный аккаунт: `sydafa` / `sydafa` (только чтение). Внутренний DBA со случайным логином и паролем в `/state/secrets.json`. `sa` DISABLE, `pdbadmin` DROP.
- Внешний host-порт объявляется в `sources.json` (`external_port`) и возвращается в объекте `connection`. Объект `connection` содержит готовый `jdbc_url` (поле `parameters` удалено как избыточное). Поле `activated_until` всегда в формате ISO 8601 UTC (`Z`).
- Источники данных объявляются в `sources.json` в декларативном формате (`schema`: структура таблиц с FQN `schema.table`, где `columns` задаётся словарём словарей `{"col": {"type": "..."}}`, а для FK — пустым словарём `{}`, с автоматическим наследованием типов из родительской таблицы; `rules`: профили правил колонок и инвариантов, например `cumulative_balance`). При первом старте создаются чистые таблицы и регистрируются правила генерации; первичное и последующее наполнение осуществляется через `POST /sources/{source}/migrate`.
- В транзакционном API миграций (`POST /sources/{source}/migrate`) все операции над сущностями используют единый FQN атрибут `entity_fqn` в формате `schema.table`. В секции `foreign_keys` внешние ссылки адресуются через единый атрибут `ref_entity_fqn`. Операции обновления и удаления поддерживают лимит случайных строк через единый параметр `limit`.
- Rules API поддерживает два уровня детализации: полный профиль таблицы (`GET`/`PUT`/`DELETE /sources/{source}/rules/{entity_fqn}`; PUT перезаписывает профиль целиком) и точечные правки (`PUT/DELETE .../columns/{column}` — генератор одной колонки; `POST .../invariants` — добавление одного инварианта с защитой от дубликата 409; `DELETE .../invariants/{index}` — удаление по позиции). Точечные маршруты объявлены в коде до маршрутов с `{entity_fqn:path}` — жадный path-конвертер иначе перехватывает вложенные пути.
- Интеграционный слой для Apache Airflow: пакет `integrations/airflow/` (`sydafa-airflow`), включающий `SydafaHook` и операторы `SydafaActivateOperator`, `SydafaMigrateOperator`, `SydafaDeactivateOperator`. Параметр `conn_id: str` обязателен.
- `/health` = готовность API, не прогрев СУБД.

## Синхронизация документации (Documentation as Code)
- **Строгое правило актуальности документации**: Любое архитектурное изменение, доработка или рефакторинг моделей, эндпоинтов, манифеста `sources.json`, операций DDL/DML, параметров генераторов или правил инвариантов ОБЯЗАНЫ одновременно и полностью отражаться в документации проекта:
  1. `README.md` — полное руководство пользователя, канонические примеры `sources.json`, спецификация эндпоинтов (`/migrate`, `/rules/{schema.table}`) и моделей;
  2. `.agents/skills/sydafa-api/SKILL.md` — скилл генерации запросов API;
  3. `AGENTS.md` — архитектурные правила и соглашения репозитория.
- Запрещено сдавать задачу или открывать Pull Request, если в `README.md` или других файлах документации остаются устаревшие контракты (например, legacy-поля, устаревшие имена ручек или неактуальные структуры конфигурационных файлов).

## Контроль веток и Pull Request (Git Workflow)
- Все новые изменения оформляются в отдельных ветках с префиксом `kodik/` (например, `kodik/feature-name`).
- Запрещено коммитить напрямую в `main`.
- **Категорический запрет на самостоятельный мерж**: Запрещено самостоятельно выполнять мерж Pull Request (командами `gh pr merge`, `git merge`, `git push` в `main` или через GitHub API). Агент имеет право ТОЛЬКО создавать Pull Request и передавать ссылку пользователю. Мерж осуществляет строго сам пользователь.
- **Ограничение на количество PR**: Запрещено без явного разрешения пользователя открывать более одного Pull Request в один репозиторий в рамках одной задачи или диалога. Все коммиты и доработки по репозиторию обязаны объединяться в единую ветку и оформляться ровно одним Pull Request.
- Обязательно создавай Pull Request и возвращай ссылки на pull request (-ы) в финальном резюме по доработкам.
- **Подробное описание PR и скоуп изменений**: при оформлении каждого Pull Request обязательно формируй исчерпывающее структурированное описание, включающее:
  - Контекст и решаемая проблема;
  - Полный скоуп изменений (Scope of Changes);
  - Список конкретных изменений по компонентам;
  - Изменения в API / моделях / контрактах;
  - Свидетельства тестирования (результаты прогона тестов).

## Документация проекта (README.md) и единая точка правды
- **README.md — главная проектная документация и единая точка правды (Single Source of Truth)** о сервисе, его архитектуре, контрактах REST API, поддерживаемых операциях, системных механизмах и сценариях использования.
- **Обязательность обновления**: при любых изменениях в кодовой базе (добавление или изменение эндпоинтов, параметров операций, DDL/DML возможностей, системных колонок или поведения сервиса) ты **обязан** синхронно обновлять `README.md`, поддерживая его в строгом соответствии с актуальным состоянием кода.
- **Приоритет над скиллами**: документация в `README.md` первична. Скиллы (включая `.agents/skills/sydafa-api/SKILL.md`) служат для ускорения прикладных задач (в частности, формулирования JSON-спецификаций из естественного языка), должны ссылаться на `README.md` как на первоисточник и не должны дублировать справочную информацию оттуда.

## Testing
- Обязательное правило: Любой новый или измененный функционал (эндпоинты, параметры, логика генераторов, операции DDL/DML) должен сопровождаться модульными тестами (в папке `test/`) и проверяться сквозным e2e-сценарием (`./test/test.sh`). Не допускается сдача задач и мерж при непройденных проверках.
- Изоляция тестирования: e2e-тесты (`./test/test.sh`) полностью изолированы (уникальный `TEST_ID=$$`, динамический свободный порт `TEST_PORT`, сеть `sydafa-test-net-${TEST_ID}`, префикс контейнеров `sydafa-test-${TEST_ID}-`). Тесты безопасны для параллельного запуска с работающим живым стендом КХД и гарантированно удаляют 100% созданных контейнеров, сетей и томов по завершении (через `trap cleanup EXIT INT TERM`).
- Стандартный сценарий полной проверки сервиса (unit + e2e):
  `./test/test.sh`
- Запуск только сквозного e2e-тестирования СУБД (MSSQL -> затем Oracle) в Docker:
  `./test/test.sh --e2e`
- Запуск тестирования конкретного источника:
  `./test/test.sh --source mssql` или `./test/test.sh --source oracle`
- Запуск быстрых unit-тестов внутри Dockerfile при сборке:
  `./test/test.sh --unit` (или `docker build -t sydafa:latest .`)
- Критерий успешности: 100% прохождение тестов (PASS всех этапов, exit-code 0).
